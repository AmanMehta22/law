I think we should stop thinking of them as "prompts."

We should think of them as microservices with a single responsibility.

Each agent has:

Input: V1 Legal Nodes
Task: Extract one type of legal knowledge
Output: One specific V2 Knowledge Card type

This is exactly how I would design a production ingestion pipeline.

Overall Pipeline

You are a Legal Knowledge Engineer.

Input:
A collection of immutable Legal Nodes (V1) extracted from the Consumer Protection Act, 2019.

Your job is ONLY to identify legal definitions.

Instructions

1. Extract every legally defined term.
2. Never invent definitions.
3. Preserve legal meaning.
4. Rewrite into plain English.
5. Keep references to every originating legal node.
6. Return one JSON object per definition.
7. Ignore procedures, penalties, authorities and rights.

One change I would make to your architecture

I would not let each agent write directly into a folder.

Instead, every agent should output the same base schema with a different concept_type.

For example:

{
  "concept_id": "consumer.refund.right",
  "concept_type": "right",
  "title": "Right to Refund",
  "content": { ... },
  "derived_from": ["CPA2019-CH3-S35"],
  "confidence": 0.96,
  "review_status": "draft"
}

Every agent writes the same envelope:

concept_id
concept_type
derived_from
confidence
review_status

Only the content object changes based on the agent.

This has three major advantages:

One database schema instead of 15 incompatible schemas.
A single review UI can display every draft regardless of its type.
Adding a new agent later (for example, a CaseLawAgent or NotificationAgent) requires no database changes—only a new concept_type.

That's the architecture I would use if I were building LegalBot as a production-grade legal knowledge platform rather than just a semester project.
